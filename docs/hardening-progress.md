# MacClippy hardening progress

## Phase 1 — backup data safety and deletion recovery

Implemented on `codex/core-reliability-hardening`. Backup validation now reads immutable snapshots without changing SQLite bytes, verifies exact SHA-256 hashes and sizes for every database/blob, requires all database files plus an empty-or-populated `blobs/` directory, rejects symlinks and unexpected files, and authenticates encrypted clipboard bodies and representations against their referenced BlobStore files. Backup creation runs the same keyed validation before publishing its snapshot.

Live restore now requires a same-installation key proof, stages and opens the full replacement storage first, journals the prior root, and rolls the whole store back after injected I/O failure or startup interruption. The rollback copy remains until the new Runtime opens and explicitly finalizes the transaction. Runtime restore shutdown stops producers, drains owned queues, and closes all storage queues under the existing store lock. Recovery records rollback completion before cleanup so another interruption can safely resume. Deletion-journal blob reads now use distinct, stable blob-ID pagination, retaining shared IDs across pages.

Backup manifests use format 2 with an encrypted key-check sentinel. Format-1 backups remain usable only when an existing encrypted database/blob payload proves the current key; an empty format-1 backup fails with `keyCompatibilityUnproven`. App-facing backup methods use `MacClippyBackupKeySource`, a sendable capability derived from the current clipboard store that does not expose the raw key. No cross-device/key migration was added.

## Phase 2 — clipboard capture and paste safety

Pasteboard capture now snapshots generation and source before materializing providers, validates the generation during and after reads, and bounds retries/provider work. A valid response from a provider that began before the deadline is retained; once it returns late, no further provider work starts. Named-pasteboard tests cover a lazy provider changing the pasteboard generation and this late-valid-response case.

Paste operations return typed `injected`, `preparedForManualPaste`, `failed`, or `cancelled` results. Cancellation uses a short independent gate so UI close/Escape does not wait on provider, pasteboard, storage, or event-post work. Queue/runtime/model callers stop on cancellation or manual preparation and retain accurate current/remaining item IDs and clipboard feedback. Snippet manual fallback preserves the prior clipboard and does not claim success.

Snippet expansion now binds queued work to the trigger's process, focused element, input generation, and expected selected-text/caret range. AX focus/selection notifications supplement the sampler, with fresh checks before commit. Delete events are prepared before commit admission; after the complete Delete sequence is admitted, the matching paste pair finishes before buffered keyboard events are replayed in order. Escape/stop close the cancellation gate without waiting for active event posting, and already intercepted key-down, key-up, and modifier events remain buffered until replay.

## Phase 3 — attachment integrity, maintenance, search, and health

Clipboard migrations 009–011 add a verified-reference marker, authenticated representation roster, and invalidation guards for body, content-kind, primary-blob, and representation mutations. Current encrypted record envelopes carry format version 1 and the roster; decoding remains compatible with old plaintext-JSON `ClipboardRecord` bodies. Legacy records whose references can be proven from authenticated bodies are indexed in cancellable bounded pages; old spilled-representation rows without an authenticated catalog proof remain unverified. A successfully authenticated legacy record without an authenticated roster may still be logically evicted by retention, but its uncertain attachments are retained as possible orphans. Wrong keys, failed body authentication, unsupported current formats, invalid markers, and damaged current rosters do not authorize deletion. Current-format backups may contain mixed old and new records; legacy payloads are still keyed-authenticated, and missing proof never promotes a legacy row to verified.

Blob read and root snapshot leases are process-wide and keyed by the canonical BlobStore root, so separate store instances share protection. Preview/image reads hold a lease from database lookup through file read; backup holds a root lease; compression, deletion, and reconciliation recheck references at their commit boundary before reclaiming files. Deferred cleanup rechecks without triggering an unbounded legacy backfill. Search migration `005-search-maintenance-indexes` adds the maintenance lookup indexes. Startup health uses bounded checks; explicit full health uses an independent read-only connection and reports whether full integrity and foreign-key checks actually ran. The storage dashboard reads indexed image blob IDs in stable pages without decrypting every envelope; this view is advisory and does not authorize garbage collection.

File-backed backup snapshots now normalize the destination database after the raw SQLite backup handle is closed, removing copied WAL mode/sidecar dependencies before hashing and keyed validation. A real WAL-backed Runtime fixture verifies the snapshot has no SQLite sidecars, validates with the installation key, and restores successfully. App lifecycle test fixtures use named pasteboards, fake both event-posting paths, disabled snippet expansion, and UUID-scoped preferences. The direct real-input-tap test is opt-in. The `MacClippyUITests` target was not run.

## Phase 4 — bounded capture and thumbnail work

Capture admission now bounds retained work to eight jobs and an estimated 256 MiB. It records bounded dropped-generation metadata and rereads only the current pasteboard generation when capacity returns. Recovery honors generations already consumed by privacy pause, Ignore Next, or MacClippy's own writes, including copies that arrive while stopped; restarting clears an unused Ignore Next budget so the next new copy is handled normally. Internal-write tokens are capped at the latest 32 generations and restart pruning atomically consumes the current token while retaining concurrently registered future tokens.

Ordinary Runtime stop invalidates its lifecycle without synchronously draining admitted work. Restore shutdown runs off-main, drains capture, maintenance, OCR, and lifecycle commits, then retires the thumbnail disk cache before replacing storage. OCR independently caps work at eight jobs/64 MiB and keeps reservations for payloads retained by canceled recognizers until those operations actually return. This prevents repeated stop/restore cycles from granting overlapping payload budgets.

File-thumbnail loading now limits decoding to two workers and 64 pending flights, caps in-memory cache cost at 32 MiB, bounds requested decode dimensions and rejects invalid sizes, and delivers results only for the active session. Ending a dock session invalidates work immediately, without waiting for its hide animation or native decoding. The Core thumbnail disk cache uses short I/O permits and a restore-only retirement fence: future I/O is rejected and already-admitted filesystem work drains before the root can be replaced. A late encoder or compression cleanup cannot write into the replacement cache.

## Phase 5 — CI minimum-OS status and isolated E2E

Clipboard records now preserve representation item identity through schema migration 012, including repeated UTIs across pasteboard items; authenticated representation rosters and the versioned envelope keep current-format replay and mutation fail-closed while legacy rows remain readable as item zero. Normal replay restores the verified native items, while plain replay derives text from the verified primary. Search repair migration 006 tracks a repair epoch and applies bounded, watermark-based pages, leaving the active index searchable while capture, edits, and search continue; page commits re-fetch current metadata so intervening edits or deletions are not overwritten. Shipping retention remains capped at 10,000 records by default; only the explicitly isolated E2E Runtime can opt into a 100,000-record corpus. The README links the CI/release guide, which documents same-SHA required-CI gating, stable version/build metadata, and main-only nightly publishing with guarded tag retargeting.
